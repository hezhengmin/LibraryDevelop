# Feature Specification: 使用者註冊服務（含電子郵件驗證與密碼加密）

**Feature Branch**: `001-user-registration`
**Created**: 2026-03-20
**Status**: Draft
**Input**: User description: "建立一個使用者註冊服務，包含電子郵件驗證和密碼加密。"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 使用者自助註冊帳號 (Priority: P1)

一位新使用者進入圖書管理系統的登入頁面，點擊「立即
註冊」連結，系統導向註冊頁面。使用者填入帳號名稱、
電子郵件地址與密碼（需輸入兩次確認），提交表單後
系統建立帳號並告知使用者需至信箱完成驗證。

**Why this priority**: 註冊是使用者進入系統的第一道門檻，
沒有註冊功能就沒有新用戶，直接影響系統的基本可用性。

**Independent Test**: 可透過填寫註冊表單並確認帳號成功
建立於系統中來完整驗證，即使驗證信功能尚未完成也能
看到帳號已被建立。

**Acceptance Scenarios**:

1. **Given** 使用者在註冊頁面，**When** 填入有效帳號名稱
   `testuser`、有效電子郵件 `test@example.com` 與符合規則
   的密碼並提交，**Then** 系統建立帳號，顯示「註冊成功，
   請至信箱完成電子郵件驗證」提示訊息。
2. **Given** 使用者在註冊頁面，**When** 填入已被其他帳號
   使用的電子郵件地址並提交，**Then** 系統拒絕註冊並顯示
   「此電子郵件已被使用」錯誤訊息。
3. **Given** 使用者在註冊頁面，**When** 填入已存在的帳號
   名稱並提交，**Then** 系統拒絕註冊並顯示「此帳號名稱
   已被使用」錯誤訊息。
4. **Given** 使用者在註冊頁面，**When** 兩次密碼輸入不一致
   並提交，**Then** 前端即時顯示「密碼不一致」錯誤，表單
   不送出。

---

### User Story 2 - 電子郵件驗證 (Priority: P2)

使用者完成註冊後，系統發送一封驗證信到使用者提供的
電子郵件地址。信件中包含驗證連結，使用者點擊連結後
系統將該帳號標記為「已驗證」。驗證前使用者無法登入
系統。

**Why this priority**: 電子郵件驗證確保使用者提供的信箱
有效，是帳號安全的基本保障，也是未來密碼重設等功能
的前提。

**Independent Test**: 可透過註冊帳號後檢查驗證信是否
發送、點擊驗證連結後帳號狀態是否更新來獨立驗證。

**Acceptance Scenarios**:

1. **Given** 使用者剛完成註冊，**When** 系統發送驗證信，
   **Then** 驗證信在 30 秒內送達使用者信箱，信件包含
   可點擊的驗證連結。
2. **Given** 使用者收到驗證信，**When** 點擊驗證連結，
   **Then** 系統將帳號標記為「已驗證」，並顯示驗證成功
   頁面，引導使用者前往登入。
3. **Given** 帳號尚未通過電子郵件驗證，**When** 使用者
   嘗試登入，**Then** 系統拒絕登入並顯示「請先完成電子
   郵件驗證」提示，同時提供「重新發送驗證信」選項。
4. **Given** 驗證連結已超過 24 小時，**When** 使用者點擊
   該連結，**Then** 系統顯示「驗證連結已過期」訊息，
   並提供重新發送驗證信的選項。

---

### User Story 3 - 重新發送驗證信 (Priority: P3)

使用者因驗證信過期、遺失或誤刪而需要重新驗證時，
可在登入頁面輸入已註冊的電子郵件地址並請求重新發送
驗證信。

**Why this priority**: 處理驗證信遺失或過期的情境，
確保使用者不會因為無法完成驗證而永遠被鎖在系統外。

**Independent Test**: 可透過請求重新發送並確認新驗證信
送達來獨立測試。

**Acceptance Scenarios**:

1. **Given** 帳號存在但尚未驗證，**When** 使用者請求重新
   發送驗證信，**Then** 系統發送新的驗證信並顯示「驗證信
   已重新發送」提示。
2. **Given** 使用者輸入不存在的電子郵件地址，**When**
   請求重新發送驗證信，**Then** 系統依然顯示「若該信箱
   已註冊，驗證信已發送」（不洩露帳號是否存在）。
3. **Given** 使用者在 1 分鐘內已請求過重新發送，**When**
   再次請求重新發送，**Then** 系統顯示「請稍後再試」
   以防止濫用。

---

### Edge Cases

- 使用者輸入格式不正確的電子郵件地址（如缺少 `@`），
  前端 MUST 即時提示格式錯誤，後端同樣進行格式驗證。
- 使用者密碼不符合最低長度要求（6 字元），系統 MUST
  在前後端同時驗證並明確提示密碼規則。
- 驗證連結被多次點擊，第二次之後系統 MUST 顯示
  「帳號已驗證」而非產生錯誤。
- 使用者用已驗證的帳號請求重新發送驗證信，系統 MUST
  顯示「帳號已驗證，請直接登入」。
- 並發註冊相同帳號名稱，系統 MUST 僅允許一筆成功，
  另一筆回傳衝突錯誤。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系統 MUST 提供使用者自助註冊功能，接受帳號
  名稱、電子郵件地址與密碼作為必填欄位。
- **FR-002**: 系統 MUST 驗證電子郵件地址格式的正確性
  （前端即時驗證 + 後端二次驗證）。
- **FR-003**: 系統 MUST 確保同一電子郵件地址不可重複
  註冊於不同帳號。
- **FR-004**: 系統 MUST 以安全的雜湊演算法儲存密碼，
  永不以明文形式儲存或傳輸密碼。
- **FR-005**: 系統 MUST 在註冊成功後自動發送電子郵件
  驗證信，信件中包含限時驗證連結。
- **FR-006**: 驗證連結 MUST 具有 24 小時有效期限，
  過期後自動失效。
- **FR-007**: 系統 MUST 阻止未通過電子郵件驗證的帳號
  登入，並提示使用者完成驗證。
- **FR-008**: 系統 MUST 提供重新發送驗證信功能，並實施
  頻率限制（每分鐘最多 1 次）。
- **FR-009**: 重新發送驗證信時，系統 MUST NOT 洩露該
  電子郵件是否已被註冊（防止帳號列舉攻擊）。
- **FR-010**: 前端註冊表單 MUST 要求使用者輸入兩次密碼
  以確認一致性，不一致時前端即時顯示錯誤。
- **FR-011**: 系統 MUST 在密碼不符合強度規則時，明確
  告知使用者密碼規則（最少 6 字元）。
- **FR-012**: 驗證成功後系統 MUST 將使用者導向登入頁面
  或顯示可點擊的登入連結。

### Key Entities

- **使用者帳號 (User)**：代表一個註冊使用者。關鍵屬性
  包括帳號名稱（唯一）、電子郵件地址（唯一）、
  加密後的密碼、電子郵件驗證狀態。
- **電子郵件驗證紀錄 (Email Verification)**：代表一筆
  驗證請求。關鍵屬性包括關聯的使用者、驗證 token、
  建立時間、過期時間、是否已使用。

### Non-Functional Requirements (Constitution Alignment)

- **程式品質**: 遵循 Controller → Service → Repository 分層，
  TypeScript strict / C# nullable enabled，通過靜態分析。
  註冊邏輯 MUST 放在 Service 層，Controller 只負責 HTTP
  請求處理與回應。
- **測試標準**: Service/Repository 單元測試覆蓋率 ≥ 80%，
  Controller endpoint 含正向與錯誤整合測試，bug fix 附迴歸測試。
  至少測試：成功註冊、重複帳號、重複信箱、密碼驗證失敗、
  驗證連結成功/過期/重複使用等情境。
- **使用者體驗一致性**: 使用 Element Plus 元件，SCSS + Tailwind CSS
  樣式，顯示載入狀態與使用者友善錯誤訊息。註冊表單風格
  MUST 與現有登入頁面保持視覺一致。
- **效能需求**: 註冊 API p95 ≤ 200ms，驗證信發送 SHOULD 在
  30 秒內送達，初始 bundle ≤ 300KB gzip。

## Scope

### In Scope

- 使用者自助註冊（帳號名稱 + 電子郵件 + 密碼）
- 密碼安全雜湊儲存
- 電子郵件驗證信發送
- 驗證連結點擊後帳號啟用
- 重新發送驗證信機制（含頻率限制）
- 前端註冊頁面與對應表單驗證
- 登入流程增加電子郵件驗證檢查

### Out of Scope

- 第三方社群登入（Google、Facebook、GitHub OAuth）
- 密碼重設 / 忘記密碼功能
- 電子郵件變更功能
- 多因素驗證（MFA / 2FA）
- 帳號停用 / 刪除功能
- CAPTCHA 驗證碼

## Assumptions

- 系統已有 ASP.NET Core Identity 基礎設施（UserManager、
  SignInManager）可直接使用。
- 密碼加密由 ASP.NET Core Identity 內建的 PBKDF2 雜湊
  機制處理，無需自行實作。
- 電子郵件發送使用 SMTP 服務（開發環境可使用 Ethereal
  或 MailHog 等測試用 SMTP 服務）。
- 驗證連結的有效期限為 24 小時，此為業界常見做法。
- 註冊頁面設計風格沿用現有登入頁面的視覺風格。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 使用者可在 2 分鐘內完成註冊流程（填寫表單 →
  提交 → 收到確認訊息）。
- **SC-002**: 95% 的驗證信在使用者提交註冊後 30 秒內送達。
- **SC-003**: 100% 的密碼以安全雜湊方式儲存，資料庫中不存在
  任何明文密碼。
- **SC-004**: 90% 的使用者可在首次嘗試中成功完成註冊與驗證
  流程，無需尋求協助。
- **SC-005**: 重新發送驗證信的頻率限制成功阻止每分鐘超過 1 次
  的重複請求。
- **SC-006**: 未驗證帳號 100% 被阻擋於登入流程之外。
